# HamBBS protocol, version 1

This document is the complete, public specification of the HamBBS wire
protocol. Amateur radio rules (ITU RR Art. 25, and national rules derived
from it) forbid transmissions encoded to obscure their meaning. HamBBS
therefore uses **no encryption**. All encodings below are open standards
(CBOR, RFC 8949; DEFLATE, RFC 1951), so anyone can decode a monitored
session with this document.

Design goals:

* **Few link turnarounds.** On half-duplex radio links, each change of
  direction costs seconds. A normal sync is one exchange: the server sends a
  banner, the client sends one batch, and the server answers with one batch.
* **Small.** Binary CBOR with integer keys plus DEFLATE compression.
* **One port for humans and programs.** A plain packet terminal or telnet
  gets a classic command-line BBS. A client switches to sync mode with a
  magic line.

## 1. Connection and mode detection

The underlying link is any reliable byte stream: TCP, AX.25 connected mode
(e.g. via Direwolf's AGWPE interface), or an HF ARQ modem.

1. The server sends a **banner line**:

   ```
   [HBBS1:<node>:<nonce>] <free text>
   ```

   * `1` is the protocol version.
   * `<node>` is the node name (`[A-Za-z0-9_.#-]+`).
   * `<nonce>` is a fresh random hex string (16 bytes = 32 hex chars), used
     once for login.
   * The free text includes the station callsign, so the banner also serves
     as station identification.

   Lines end with CR on radio links and CRLF on TCP. The server may then
   send more text and a prompt (`Callsign: ` on TCP, or `NODE> ` on radio).
   Sync clients ignore it.

2. The client sends the line `#HBBS1` terminated by a **single CR**
   (`0x0D`, no LF). Anything else is treated as terminal input; see §5.

3. The server answers `#HBBS1 OK` terminated by a single CR. Frames follow
   immediately. Clients should skip input until they see a line *containing*
   `#HBBS1 OK`, because it may share a line with a prompt.

   The client does **not** wait for this line before sending its frames. It
   sends the magic line and its whole batch in one transmission.

## 2. Framing

```
frame   = length type payload
length  = unsigned LEB128 varint: number of bytes in (type + payload), 1..1048576
type    = 1 byte: bit 7 = DEFLATE flag, bits 0-6 = frame type
payload = CBOR map, or raw DEFLATE (RFC 1951, no zlib header) of a CBOR map
          if the flag is set. May be empty.
```

Senders compress a payload only when the result is smaller (in practice for
payloads of 64 bytes or more). Decompressed payloads must not exceed 1 MiB.

All CBOR maps use **small integer keys**, listed per frame below. Unknown
keys must be ignored, which allows compatible additions.

## 3. Frame types

| Type | Name      | Dir | Payload |
|-----:|-----------|-----|---------|
| 1    | HELLO     | C→S | 1 call (text), 2 version (int), 3 sig (bytes), 4 pubkey (bytes, optional), 5 client (text, optional) |
| 2    | WELCOME   | S→C | 1 call, 2 node, 3 registered (bool), 4 motd (text) |
| 3    | SYNC      | C→S | 1 since (int), 2 areas ([text]), 3 fetch_personal (bool), 4 fetch_areas ([text]), 5 after (int, unix s), 6 limit (int) |
| 4    | HEADERS   | S→C | 1 cursor (int), 2 more (bool), 3 headers ([Message], without body) |
| 5    | GET       | C→S | 1 ids ([text]) |
| 6    | PUT       | C→S | 1 messages ([Message]) |
| 7    | MESSAGES  | S→C | 1 messages ([Message], with body) |
| 8    | PUTRESULT | S→C | 1 accepted ([text]), 2 rejected ([{1 id, 2 reason}]) |
| 9    | END       | both | empty: end of batch, the other side's turn |
| 10   | BYE       | both | empty: end of batch and of session |
| 11   | ERROR     | S→C | 1 code (int), 2 text. The server closes after sending it. |

**Message**:

| Key | Field   | Notes |
|----:|---------|-------|
| 1   | id      | 6–32 chars `[A-Za-z0-9_-]`, globally unique. Generated by the author's client. Clients use 12 chars (classic BID length). |
| 2   | seq     | server sequence number (server→client only) |
| 3   | kind    | `"P"` personal, `"B"` bulletin |
| 4   | from    | author's base callsign; the server overwrites it with the authenticated call |
| 5   | to      | `CALL[@NODE]` for P, `AREA[@SCOPE]` for B |
| 6   | subject | ≤ 80 characters, single line |
| 7   | body    | UTF-8, LF line endings. Omitted in HEADERS. |
| 8   | size    | body length in bytes (HEADERS only) |
| 9   | created | unix seconds |
| 10  | expires | unix seconds, 0 = never |
| 11  | origin  | node where the message entered the network |
| 12  | path    | [node], nodes traversed |

Error codes: 400 bad request, 401 authentication failed, 403 forbidden (for
example, callsign ≠ link address), 404 unknown callsign with closed
registration, 426 unsupported version, 500 server error.

## 4. Session flow

The client batch is processed in order. A typical sync:

```
S: [HBBS1:LA1BBS:9f2c...] Oslo BBS de LA1ABC (HamBBS)\r Callsign:
C: #HBBS1\r  HELLO  PUT  SYNC  GET  BYE          (one transmission)
S: #HBBS1 OK\r  WELCOME  PUTRESULT  HEADERS  MESSAGES  MESSAGES  BYE
```

* **HELLO** must be the first frame.
* **PUT** comes before SYNC so the response reflects the upload. Messages
  whose ID is already stored count as *accepted*, so resending after a lost
  response is safe.
* **SYNC** returns everything visible to the user with `seq > since`:
  personal mail addressed to them, and bulletins (restricted to `areas` if
  that list is non-empty). Message bodies are included in a MESSAGES frame
  for personal mail if `fetch_personal` is set, and for bulletins whose area
  is in `fetch_areas` (`"*"` = all). Everything else is listed in HEADERS.
  The client stores `cursor` and sends it as `since` next time. It must only
  do so after the whole response has been processed. If `more` is set, the
  server's limit was reached and the client should sync again. `after`
  limits a first sync to recent messages.
* **GET** fetches bodies for headers the user chose earlier, usually in the
  next session. This avoids a second turnaround.
* A client may end its batch with **END** instead of BYE to keep the
  session open. The server answers its batch followed by END.

### Authentication

There are no passwords on the air. Each user has an Ed25519 key pair derived
from callsign and password:

```
seed = Argon2id(password, salt = "hambbs-v1:" + BASECALL, t=1, m=64 MiB, p=4, len=32)
```

`sig` in HELLO is the Ed25519 signature of the ASCII string

```
HBBS1|<node>|<BASECALL>|<nonce>
```

with `node` and `nonce` taken from the banner. The server verifies it with
the stored public key. On first login, with open registration, the server
stores `pubkey` from HELLO. The server stores no passwords, and a monitored
session cannot be replayed (the nonce changes on every connection).

Signing is not encryption. Every byte of the session stays readable to
anyone monitoring.

On links that carry a verified source callsign (AX.25), the server also
requires `call` to match it.

## 5. Terminal mode

Any first line other than `#HBBS1` starts a classic text session.

* **TCP:** the first line is the callsign, then the server asks for the
  password, which is checked against the same derived key. Telnet is not
  radio, but this password is in clear text on the wire; use sync clients
  over untrusted networks.
* **Radio:** the link-layer callsign identifies the user, as on every
  classic packet BBS. No password is used.

Commands: `L` (new), `LL [n]`, `LM`, `LB [AREA]`, `A`, `R n`, `S CALL`,
`SB AREA`, `K n`, `I`, `H`, `B`. While writing a message, end the text with
`/EX` on its own line or with Ctrl-Z, or type `/ABORT` to cancel.

## 6. Versioning

Additions use new CBOR keys or frame types and keep version 1. Incompatible
changes increase the number in `HBBS<n>`, `#HBBS<n>` and HELLO.version.
